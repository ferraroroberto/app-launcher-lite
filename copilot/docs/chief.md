# The lite fleet chief: helpers

app-launcher-lite carries both sides of the fleet chief. The launcher (`app/`, `src/`) holds the plan and journal cards, the mailbox, the doorbell and the dispatch brief. This `copilot/` folder holds the helper side: the code the chief session runs and the state files the launcher reads. Every state file keeps the full fleet's format byte for byte, so the launcher's readers parse it unchanged; only the location differs, `~/.copilot/app-launcher-lite-state/` instead of `~/.claude/hooks/state/`.

## The chief skill

`.github/skills/chief/SKILL.md` is the chief's brain. app-launcher-lite spawns the chief session with this checkout as its working directory and types `/chief`. Copilot discovers the skill as a project skill from `.github/skills/`, so it loads only in sessions started here and is not one of the skills `install.py` junctions into `~/.copilot/skills/`. A check for a `skills/chief/SKILL.md` under the Copilot home therefore finds none, and that is expected.

It is written for any model behind Copilot. It gives one table from what woke the chief (a message, the doorbell, a mailbox event kind, the Board's answers) to the verbs to run, plus the rails `dispatch` enforces and those it cannot. It also sets two habits: decide only from `chief_ops.py`'s `KEY=value` lines, with a missing line counted as unknown, and end every turn with a standalone summary and no in-turn waiting, because the doorbell (when on) or Roberto's next message is what wakes it. A lane that stops blocked is steered on by the chief itself; only a real decision becomes a Board question. It names only verbs this checkout carries.

## Entry point

The chief calls one CLI, `skills/_lib/chief_ops.py`, through the launcher `install.py` writes to `<Copilot home>/hooks/app-launcher-lite-chief-ops.cmd`, where the Copilot home is `COPILOT_HOME` when set and `~/.copilot` otherwise, in the installer and in the skill's command alike. The launcher carries this checkout's interpreter and script paths, so the one command `& "$(if ($env:COPILOT_HOME) { $env:COPILOT_HOME } else { "$HOME/.copilot" })/hooks/app-launcher-lite-chief-ops.cmd" <verb>` works from any working directory; the chief's folder is `copilot/`, which has no `.venv` of its own. `chief-ops` below stands for that command. The chief acts only on the `KEY=value` lines it prints to stdout. Breadcrumbs go to stderr. A refused write exits 2 with `ERROR: ...` on stderr and leaves the state file as it was.

```powershell
chief-ops plan show
chief-ops plan add <repo>#<N> "<title>" [--status S] [--model M] [--kind K]
chief-ops plan lane <repo> building|gate|idle|waiting [--item "#N" | --item skill:<name>]
chief-ops plan ask "<question>" --ref <repo>#<N> --option "Label::why" ...
chief-ops plan unwait <id>       # UNWAIT=none id=<id> (exit 0) when nothing waits under it
chief-ops plan prune             # drop merged rows
chief-ops note "<one line>" [--kind K] [--ref <repo>#<N>]
chief-ops inbox [--count]     # claim pending mailbox events
chief-ops ack <id> [<id> ...]  # retire handled events
.venv\Scripts\python.exe skills\_lib\chief_managed.py mark <sid> <repo> <number>
chief-ops board | sessions | chief-sid
chief-ops dispatch <repo> <N> [--mode start|yolo] [--model M] [--brief-file F]
chief-ops open <project> [--message-file F] [--issue N | --lane]
chief-ops file <repo> --title T --body-file F
chief-ops say <sid> --file brief.md --verify
chief-ops exchange <sid> | stop <sid> [--kill]
chief-ops issues <repo>#<N> ...
chief-ops verify <repo> --expect mr-open|merged [--branch B]
chief-ops doctor [--checkout PATH] [--issue-ref <repo>#<N>]
```

`doctor` is a read-only check of this machine's chief setup (`skills/_lib/chief/doctor.py`, logs in `chief/doctor_logs.py`). It prints one `CHECK <area>.<name>=pass|fail|unknown ...` line per fact and ends with `DOCTOR=pass|fail|unknown fails=<n> unknowns=<n>` (exit 0 only on pass). Install: the checkout's commit and how far it is behind `origin/main` as of the last fetch, the Copilot CLI version, the `.venv` interpreter, each installed hook config against what `install.py` renders now (`render_hook_config`, `render_chief_launcher`), every hook command's target file, the installed skills (a junction to this checkout, or a marked copy with the same content; on a shared machine the full fleet owns the folder), and the chief launcher, which must answer `chief-sid`. Verbs: each read verb the chief uses runs as a child with its expected line and its time. Mailbox: pending and claimed events with the oldest age of each (pending past the fallback waiter, or a claim unacked past the stale window, fails), and whether the launcher's `chief_doorbell` agrees with `wake`. Logs: `ERROR`/`CRITICAL` lines and tracebacks of the last 24 h in Lite's `webapp/*.log`, and hook errors in Copilot's `logs/`, grouped by message once ids and numbers are masked; Copilot's other errors and its hook warnings are notes. A check that cannot establish its fact is `unknown`. Every line is redacted (`<home>`, `<user>`, `<host>`, `<checkout>`, `<copilot-home>`). `--checkout` compares the install with another checkout, for running a worktree's doctor against the primary's install. The diagnostics run built on it is `docs/chief-diagnostics.md`.

Launcher calls go to app-launcher-lite on the webapp port its own `config/config.json` sets (`webapp.port`, default 8465; read by `skills/_lib/lite_ports.py` from app-launcher-lite's own `config/config.json`, the checkout `copilot/` sits in, or from the file `FLEET_LITE_CONFIG` names, so a Lite running beside another launcher is the one addressed; `--base-url` overrides; any non-loopback host is refused). The scheme in that URL is only a hint: `skills/_lib/lite_webapp.py` asks the port once per process with a plaintext probe and uses HTTPS or HTTP, whichever it serves, so every `serve_over` mode (`http`, `https`, `both`, `auto`) works with no setting on the chief's side; certificate checks are off because the host is loopback. The session-host port is never probed and stays plain HTTP. A launcher that stays silent or drops the connection prints `UNCONFIRMED=...`, one that refuses the connection prints `UNREACHABLE=...`, and one that answers in the other protocol after Lite restarted with another `serve_over` prints `WRONG_SCHEME=...` for a write, which is never resent (a read retries once over the new scheme, and the next call uses it); none is folded into a verdict. Repos are found under app-launcher-lite's `projects_dir` (`config/webapp_config.json`; read by `skills/_lib/lite_repos.py`), or beside the checkout when that is empty, relative or not a folder, so `<projects_dir>/<repo>` is where `dispatch`, `verify`, `merge` and `sweep` look. Forge reads go through `glab` against `<namespace>/<repo>` on GitLab. The namespace is app-launcher-lite's `gitlab_group` (`GET /api/config` on loopback); when that is empty, the checkout's own `origin` remote names it, and `--owner` overrides both on `issues`, `verify` and `merge`. `dispatch`'s owner check, `drain` and `sweep` resolve it the same way. The host works like the namespace: `gitlab_host` from the launcher, else the host of the checkout's `origin` (a GitHub remote does not count), else gitlab.com. Every chief and owner-check `glab` call carries it as `GITLAB_HOST`, because `glab` sends a bare `<namespace>/<repo>` to gitlab.com, which answers a self-hosted project with a 404. A `glab` failure on `issues`, `verify`, `merge` or an owner-check read ends with `(tried host <host>, project <path>)`, so a wrong host or group reads off one line. The token stays in `glab`'s own store (`glab auth status` shows it per host); the chief never reads, stores or logs one. When no source names one, the read is `OWNER=unknown` (`issues` exits 1, `verify` prints `STATUS=UNKNOWN`, `merge` prints `MERGE=unknown`), never a 404 that reads as "no such issue". When `glab` is missing or signed out, `issues` prints an `error:` row for the ref and `verify` prints `STATUS=UNKNOWN`.

`dispatch` keeps fleet-config's rails verbatim (`chief/rails.py`). It refuses before the POST if the repo is occupied, the worker cap is reached, a yolo is unconfirmed, the issue carries `needs-owner`, or a fleet-wide brief would run while a fleet-wide Job is running. It also refuses when one of the four issue skills is not found: it reads the launcher's `GET /api/board/chief/skills` first, and a missing or unknown skill, or a check that does not answer, prints `REFUSED=` naming the skill. The launcher's `POST /api/board/issues/start` refuses the same case with a 409, which covers the Board's own start buttons, and `dispatch` prints that reason as `REFUSED=launcher refused the start (http-409): ...`. A spawn the launcher may still be running prints `DISPATCH=unconfirmed` and must not be retried. `--model` is a Copilot model id, sent to the launcher as typed.

`open <project> [--message-file F] [--issue N | --lane]` starts a Copilot session in a Coding-tab project through `POST /api/apps/<id>/launch`. It refuses an unknown project, an occupied one and a full worker cap before the POST, as `dispatch` does. Plain by default: the session is never marked chief-managed, never enters the plan, and is left running (`stop` ends it), so its end never reaches the mailbox. A plain open whose message runs lane work (an `/issue-*`, `/upstream-sync`, `/downstream-sync` or `/cleanup-fleet` command) is refused before the POST for that reason, and so is a `say` carrying one into a session that is not chief-managed (`REFUSED=`, exit 2, naming `chief_managed.py mark`). `--issue N` (or `--lane` for a queue with no single issue, recorded with a null `number`) makes it a lane: right after the spawn and before the first message it is marked chief-managed with a fresh dispatch id, printed as `DISPATCH_ID=`, so its hooks publish turn-end and session-end events like a dispatched worker's. Every open sends a request id (printed first as `REQUEST_ID=`) with the launch. The launcher keeps a record per id for the life of its process, so a launch that outlives the 60 s launch budget (the session-host's own create call allows 45 s) is polled by that id instead of posted again, and a repeat with the same id answers from the record and never opens a second session. A launch still not confirmed after the poll prints `OPEN=unconfirmed` and exit 1; resume it with `open <project> --request-id <id>`, never with a fresh `open`. A resumed open skips the occupancy and cap rails only when the launcher holds that id, and sends its message only after the transcript shows no copy of it. The launch route takes no prompt, so the message goes in afterwards, once. A message sent while Copilot is still drawing its TUI is dropped although the launcher answers `delivered`, so `open` waits `--settle` seconds (default 10) after the spawn, posts once, and then waits for the message as a user turn. When the session-host acknowledges the input with an `input_id` and `written_at` and the exchange read reports its newest user turn's time (`latest_user`), a turn recorded at or after that write is the proof, so an identical earlier prompt is never taken for this one. When either side is too old to say, `open` matches the message text against the transcript's user turns instead. Only that prints `OPENED session=<sid>` and `DELIVERED`. A transcript that stays empty prints `STRANDED`, an unreadable one `UNKNOWN`, each with `SESSION_LIVE session=<sid>` and exit 1: the session runs without its message, and resending or stopping is the caller's call. A send that gets no answer within 35 s (the launcher's own hold for a just-spawned TUI plus its input call) is not resent, and the transcript is still watched, because the write may have landed. Every open ends with three lines that state each fact on its own: `LAUNCHED=` (the session exists), `PROMPT_DELIVERED=` (the launcher accepted the first input, or the transcript shows it) and `EXCHANGE_CONFIRMED=` (a user turn after the acknowledged write, or the transcript text, shows it). Each is `yes`, `no`, `unknown` (not established, never folded into `yes`) or `none` (no message was asked for), with a `reason=` where it is not plainly `yes`; exit 0 only when every fact due is `yes`.

A lane carries an issue (`--item "#N"`) or a skill run with no issue behind it (`--item skill:<name>`, a lowercase name such as `skill:upstream-sync`); `chief_plan.py` refuses any other item. The Board's plan card shows a skill lane's item as the skill's name, with no issue link. The chief opens such a lane with `open <repo> --lane --message-file <path>`, the file holding the skill command, and records it with `plan lane <repo> building --item skill:<name> --session <sid>`. A lane runs Lite's bundled skills (`issue-start`, `issue-yolo`, `issue-finish`, `issue-add`, `e2e`, `quick`) on any machine, and another skill only where the Copilot home holds `skills/<name>/SKILL.md`.

`plan unwait <id>` that matches no waiting item writes nothing and prints `UNWAIT=none id=<id>` with exit 0. An instruction typed into the chief's terminal is not a Board answer, so there is nothing to clear and the no-op must not read as a failed call. An index out of range is still refused with exit 2.

`sessions` gives the Board 5 s, because the Board joins transcript reads that stall under load. Past that it answers from `GET /api/claude-code/roster`, one bounded session-host list with no transcript read, and prints `SOURCE=session-host reason=...` above the rows; each row's status is the host's lane state, `spawned`, `working`, `awaiting-input` or `unknown`. A roster that also fails is reported as its own state, never as an empty roster.

`say <sid> --file F [--verify]` sends one steer. Plain `say` is one POST: `FAILED` leaves the resend to the caller. `--verify` recovers from a transient transport failure (connection refused, unreachable, reset, timeout, or a session-host 503) with at most 3 sends, waiting 1 s, 2 s and 5 s after each failure, and the exact-text check gates every resend: before it sends again it reads the session transcript, and a user turn carrying the steer text that was not there before the first send ends the call as `DELIVERED` with no further POST. A readable transcript without the text allows the resend. An unreadable one allows it only while every failure so far was a refused or unreachable connection, since after a timeout or reset the write may have landed. An HTTP negative (502 not ingested, 409 session gone, 400 or 403 refused) is `STRANDED` and never retried. After the last attempt a readable transcript with no copy is `PENDING` and an unreadable one is `UNKNOWN`, each with the attempt count; neither is a delivery, and exchange movement alone never makes one. The sid prefix lookup reads the board with the same bounded retry, so a launcher that restarts between the chief's call and the lookup is waited out before anything is sent. The same transcript proof ends a successful send as `DELIVERED` too, ahead of the exchange poll.

`file <repo> --title T --body-file F` files one GitLab issue through the launcher's `POST /api/board/issues/file`, the route the Board's file button uses, so the chief files without any `glab` write of its own. The body comes from a file and the route takes no labels, so a filed issue has none and its lane's `issue-start` treats it as plan mode. It prints `FILED=<repo>#<N>` and `URL=<issue url>`; `REFUSED=<reason>` (exit 1) for an empty title or body, an unreadable body file or any 4xx the launcher answers (unknown project, over-long title or body); and `UNCONFIRMED=...` (exit 1) for a timeout, a 5xx or a reply with no issue number, because the issue may exist and a retry can file a duplicate. A launcher that refuses the connection prints `UNREACHABLE=...`. The launcher appends its own footer to an issue filed with the delegate token.

`verify` is lite's own: the lane ships through a GitLab merge request, so `--expect mr-open` means a clean checkout plus an open merge request from the branch, and `--expect merged` means a clean checkout back on the default branch plus a merged one. It prints the same `STATUS=CLEAN|DIRTY|UNKNOWN`, `BRANCH=` and `REASON=` lines as upstream.

| Subcommand | Writes | Read by (app-launcher-lite) |
|---|---|---|
| `plan ...` | `chief-plan.json`, format v1; each transition also journalled | `src/chief/plan.py`, `src/chief/queue_status.py`; `src/chief/plan_prune.py` loads `chief_plan.py` by path and calls `prune_plan_file` |
| `note ...` | `chief-journal.jsonl`, one JSON line per event, beside the plan file | `src/chief/journal.py` |
| `inbox`, `ack` | claims events into `chief-inbox/.claimed/`, deletes them on ack; a claim unacked for Lite's `chief_reoffer_minutes` (default 15) is offered again | the chief itself; the launcher publishes `session-end`, `job-failed`, `cap-raised` and other events into the same directory |
| `chief_managed.py mark` | `chief-managed.json`, one row per chief-dispatched launcher session | called by the launcher's `POST /api/board/issues/start` through `<this repo>/.venv/Scripts/python.exe`; read by `hooks/chief_inbox.py` and the launcher's reaper (`src/chief_session_end.py`) |

The state directory is `~/.copilot/app-launcher-lite-state/`, or `COPILOT_HOOKS_STATE_DIR` when set (the same override `hooks/session_state.py` honours). `skills/_lib/fleet_core/hooks_state.py` is the one place that resolves it.

## The mailbox

A worker the chief dispatched has its launcher session id in `chief-managed.json`. On that worker's `agentStop` and `sessionEnd`, `hooks/chief_inbox.py` (called from `hooks/session_state.py` on the same hook invocation) publishes one event file into `chief-inbox/`, in fleet-config's mailbox v2 format: `kind` `turn-end`, `turn-failed` or `session-end`, `event` `Stop` or `SessionEnd`, the registry row's `repo`, `number` and `dispatch_id`. The turn end is read by the Lite checkout's one Copilot turn reader (`src/transcript_flavors/copilot_turn.py`, loaded by path): a turn whose last model round closed with no reply is `turn-failed`, with Copilot's `session.error` text as `error` when it logged one; a turn end with a background shell or sub-agent still running carries `busy: true`, a clean one `busy: false`, and an unreadable transcript leaves `busy` out (unknown). A failed turn shares the turn-end debounce and stamp. Every other session returns before any I/O. A second `turn-end` from one session within 45 s is not written. An unreadable registry writes nothing and logs that the state was undetermined.

Each publish leaves a `.<kind>-<sid>.stamp` file in `chief-inbox/` whose mtime is when it went out. The hook, the launcher's reaper (`src/chief_session_end.py`) and its reconciler (`src/chief/reconcile.py`) read and write the same stamps, so a lane gets one `session-end` however many of them see its exit. The reconciler covers a hook that never fired: every 15 seconds the canonical launcher reads each managed lane's `events.jsonl`, through the hook state row that names it, for Copilot's own `session.task_complete` or logged `agentStop` hook (a turn ended; an interactive or blocked turn writes only the second; an `agentStop` whose hook input names a `parentAgentId` is a sub-agent's, not the lane's, and is skipped) and `session.shutdown` (the session ended). A turn end or exit older than 30 seconds that no stamp covers gets one event with `source: reconcile`; a failed turn is published as `turn-failed`, dated by its round's close when no turn-end marker followed it. That includes a real second turn end the 45 s debounce held back, because the debounced write leaves the stamp at the first one's time. A `user.message` or `assistant.turn_start` after the last turn end means a turn is running, so an active lane gets nothing. The doorbell rings for the event like any other.

Copilot's `agentStop` payload carries no reply text, only `transcriptPath`, the session's `events.jsonl`. The excerpt is therefore the newest `assistant.message` content in the last 256 KiB of that file (`excerpt_source: transcript`, at most 1,500 characters). Copilot wakes a session whose background shell completes and starts a new turn (seen live on CLI 1.0.114), so a `busy` turn end is followed by another turn end when the shell is done.

Not carried: upstream skips a nested print-mode child (a `claude -p` a lane starts) that inherits the lane's `APP_LAUNCHER_SESSION_ID`. Copilot exposes no entrypoint marker for that, so a `copilot -p` run from inside a chief-managed lane still writes events as the lane. The chief dedupes by `id` and reads the exchange, so the cost is a spurious wake.

## Merge path

`chief_ops.py mr-create <N> [--timeout S]` opens the current branch's merge request for the lite `issue-finish` skill, which `git push`es first. It runs `glab mr create --fill --yes --push=false` with stdin closed and a kill timeout (60 s by default), so glab can never wait on a confirmation nobody reads and leave an orphaned process holding the lane's worktree folder. It prints `MR=created url=<merge request url>` (exit 0), or exits 1 on `MR=failed reason=<glab's first message line>`, `MR=timeout reason=...` (glab gave no answer and was killed, so the request may or may not exist: read it with `glab mr view` before retrying) or `MR=unknown reason=glab not installed`. A clean exit with no request URL is `failed`, never `created`.

`chief_ops.py rerun-job <job_id> <run_id>` answers a `job-failed` event: it re-runs the failed run's Job once, through `POST /api/jobs/<id>/run`, and only when the Job's `rerun_safe` is a literal `true` in `GET /api/jobs` (the owner sets it; the verb never writes a Job). It prints `RERUN=started ... rerun=<run id>`, `RERUN_REFUSED=<job> reason=<why>` (exit 2: `not-rerun-safe`, `rerun-safe-absent`, `rerun-safe-not-boolean`, `job-not-found`, `run-not-failed`, `already-rerun`, `is-a-rerun`), `RERUN=unknown` (exit 1: the jobs list, the failed run's record or the ledger could not be read, never counted as safe or as failed) or `RERUN=unconfirmed` (exit 1: the POST got no answer, so the launcher may have started the run). Once per failure: `chief-job-rerun.json` in the hooks state dir records the failed run before the POST, so an unanswered POST still spends the re-run, and it records the run the verb started, so that run's own failure is refused as `is-a-rerun` and the chief never loops. The verb never sends `confirmed=1`, so a Job that needs a confirm tap is out of reach (and cannot carry `rerun_safe`). The ledger holds ids only, never job output.

`chief_ops.py merge <repo>#<N> --branch <branch> [--ask]` asks GitLab to merge the lane's merge request as soon as its pipeline passes (`glab mr merge --auto-merge --squash --remove-source-branch --yes`), then reads the request back with `glab mr view`. GitLab's state, not the command's exit code, is the verdict: `MERGE=merged`, `MERGE=queued` (auto-merge set, the pipeline still running), `MERGE=refused reason=<GitLab's first message line>` or `MERGE=unknown` when glab is missing, signed out or unreadable. With `--ask`, a refusal becomes a question on the chief's plan, id `merge-<repo>-<N>`, reused on a repeat refusal and journalled like any `plan ask`. So a merge GitLab refuses reaches Roberto's Board instead of stopping silently in a lane. The lite `issue-finish` skill merges through this verb and passes `--ask` in chief-dispatched sessions. glab boxes its failures under a bare `ERROR` banner, which the reason skips, and when its message is only a retry lead-in (a 405 right after another merge) the reason gets the request's own `detailed_merge_status` appended, such as `conflict`. A merge and a conflict refusal, each with its `--ask` question, ran live on a GitLab test project.

## Worktrees, claims and sweep

Two sessions on one repo collide in the study phase, long before either cuts a branch. The lite issue skills therefore claim the repo first, with `skills/_lib/worktree_claim.py`, a byte-identical port. The first session owns the primary checkout (`MODE=primary`). Every later one, and every launcher or chief lane (`--force-worktree` when `APP_LAUNCHER_SESSION_ID` is set), builds in a sibling worktree `<repo>-wt-<N>` with the primary's `.venv` junctioned in. The claim lives in the repo's git common dir in the full fleet's format, so the full and lite helpers see each other's claims on a shared checkout. `issue-finish` removes the worktree (junction first) and lands the primary (`land-primary`, one `PRIMARY=` line), or, in the primary, runs `assert-owner`, the untrack-guarded fast-forward and `release`. `land-primary`'s service guard reads the full fleet's machine-local projects table, which lite does not carry, so it reports that it could not read the declaration instead of claiming a service is down.

`chief_ops.py sweep [--apply]` classifies finished lane worktrees with the ported `chief/chief_sweep.py`. A worktree is finished once a merged request covers its HEAD. The lookup dispatches on the remote's host: `glab mr list` for GitLab, normalised to the `gh pr list` rows the scan reads, and the ported `gh` lookup for GitHub. The sweep folder is the parent of this checkout, which on a full-fleet machine also holds that fleet's worktrees. So lite keeps only worktrees of lite repos (named in lite's own registry or active-issue markers, or named `*-lite`). Every other worktree is listed as `OUT_OF_SCOPE=` and never removed.

## Owner checks and drain

`skills/_lib/owner_check/` is fleet-config's owner-check package. `block.py`, `rule.py`, `backfill.py`, `reclassify.py` and `repair.py` are byte-identical ports. `cli.py` is upstream's with one later line (its `clear` matches merged siblings on the whole step). A note's `run` lines (where each runs, and the literal command) and `expect` are read and listed, but Lite's `mark` and `finish` do not write them yet, so a note Lite posts carries neither and the Board says no command is recorded. The forge seam `github.py` keeps upstream's module name and every function they call, but answers through `glab` against GitLab: issue view, notes and closing merge requests via `glab api`, labels via `glab issue update`, and merge request files via the `diffs` API. A failed call raises `GhError`, which every caller reports as `unknown`. The launcher's Board (`cli.py list --json`, `clear`), lite `issue-start`'s gate (`cli.py gate <repo>#<N>`), `dispatch`'s owner rail and `plan add --kind owner` all read it.

Labels are plain `needs-owner` and `needs-validation` by default, which work on any GitLab tier. Opting in with `[owner_check] label_scope = "<scope>"` in this repo's `.fleet.toml` writes GitLab scoped labels instead (`<scope>::needs-owner`, one of a kind per issue). Reads map them back to the plain name, so every reader's `"needs-owner" in labels` check is unchanged. On gitlab.com's free tier the one-of-a-kind rule is not enforced (an issue held both scoped labels at once), so scoped labels behave as plain ones there. The fleet is every sibling checkout with a GitLab remote. GitLab numbers merge requests apart from issues, so a "PR" in the package's vocabulary is a merge request iid.

`chief_ops.py drain [--dry-run]` is fleet-config's `chief/drain.py` with four seams changed. It scans the open issues of the lite GitLab fleet through `glab`, gets the audit-managed marker from `issue_host`, has no machine-local projects table (so no repo is switched off from auto-ship), and dispatches through the lite rails. Its generic brief is `chief/drain_brief.md`, which is lite's own. With Settings' `auto_drain` on, it queues open audit issues that need no owner step and dispatches queued rows into free worker slots in plan order. `chief_ops.py slots-idle` is drain's idle-slot line (`SLOTS_IDLE=<n|unknown|off> reason=...`), which the guard hook reads; `off` and `0` never hold.

## Guard hooks

`hooks/chief_guard.py` is registered for four Copilot events through `hooks/chief-guard.template.json`, which `install.py` renders next to the session-state config. Each behaviour was verified live by `scripts/copilot_probe.py`: on CLI 1.0.112, `sessionStart` `additionalContext` reaches the model, `agentStop` `decision: block` forces another turn, and `preToolUse` `permissionDecision: deny` stops the tool call; on CLI 1.0.114, `userPromptSubmitted` `modifiedPrompt` replaces an interactive session's expanded skill (manual item `prompt_hook_replaces_skill`). Each `sessionStart` and `preToolUse` answer is emitted in both Copilot's own fields and the Claude Code `hookSpecificOutput` shape Copilot also reads.

- **`sessionStart`**, chief only: the handover log `chief-handover.md` comes back as `additionalContext` (its last 24,000 characters), so a boot, a resume or a compaction never starts without the chief's intent. No log means a one-line note to start one.
- **`agentStop`**, chief only, and never while Copilot is already continuing after a hold (`stop_hook_active`). It holds the turn end with a reason naming the next command, in this order, each at most once per 10 minutes (Lite's `chief_hold_minutes`, Settings > Chief > Timings): `compact-due` prints `COMPACT_DUE percent=..` (not when `self-compact` already queued one); `slots-idle` reports free worker slots while plan rows wait as `queued` and no `plan ask --id slots-idle` covers it. It never asks Roberto for the launcher's doorbell: that switch is the owner's Setting in the launcher, not a request the chief makes (below). An unknown reading never holds.
- **`preToolUse`**: the chief's shell call that reaches the launcher's `/api/apps/<id>/launch`, `/api/board/issues/start` or `/api/claude-code/sessions/<sid>/input` route directly is denied, and the reason names the `chief_ops.py` verb to use (`dispatch`, `open --issue N` or `--lane`, plain `open`, `say`): a session opened or steered that way is never chief-managed, so its turn ends never reach the mailbox. `chief_ops.py` makes the same calls from Python, so it is not affected. `ask_user` is denied for the chief and for every chief-managed lane, because it renders only in that session's terminal. A chief-managed lane's shell call (`powershell`, `bash`) is also denied when it starts a `gh` command, names `notify_complete`, or runs a helper under a Claude Code user-scope `skills/` folder or the full fleet's checkout `skills/` folder. The reason names this checkout's `skills/` so the lane retries with lite's helper. On a PC that also runs the full fleet, that fleet's own `preToolUse` hook has already rewritten the command to a `context_filter_cli.py ... --encoded <base64>` wrapper by the time this guard runs, so the guard judges the decoded command, and the wrapper's own path (in that fleet's `hooks/` folder) is not a match. Every other tool, and every other session, passes untouched.
- **`userPromptSubmitted`**, any session app-launcher-lite's session-host lists: a prompt that invokes a skill this checkout also ships, expanded from another folder, comes back as `modifiedPrompt` with that skill block holding this checkout's `SKILL.md` (next section). A prompt whose skill already comes from this checkout, a skill lite does not ship, and a session the host does not list pass untouched.

## Lanes on a shared machine

The launcher types `/issue-start <N>` into a lane, and Copilot resolves it to the user-scope skill. On a PC that also runs the full fleet, `install.py` leaves `~/.copilot/skills` alone, so that skill is the full fleet's GitHub one: it would run `gh` and its own completion ping. The ordering Copilot applies, probed on CLI 1.0.114 with `copilot skill list --json` and a live run: project skills (`.github/skills`, also those of a `--add-dir` folder) beat personal skills, and personal skills beat folders added through `COPILOT_SKILLS_DIRS` or `copilot skill add`, which are dropped on a name clash. A lane's working directory is the repo it works on, not this checkout, so lite's skills cannot arrive as project skills without a launcher flag.

`dispatch` therefore always opens the brief it sends with `lane_preamble` (`skills/_lib/chief/lite_lanes.py`): the paths of the lane's `issue-start` or `issue-yolo` and `issue-finish` (in Lite's `skills_dir` when that setting names a folder, else this checkout's bundled copies), the instruction to use `glab` and the helpers under this checkout's `skills/_lib`, the statement that the issue's repository is the session's working directory, and the rule to keep fixing red gates, e2e failures and blocking review findings until the issue is merged or genuinely blocked (an owner step, a destructive git confirmation, an unresolved environment problem, or a failure still red after the bounded retry), with exactly one adversarial review per yolo run. That rule lives in the preamble because a machine's own skills repo may not say it. A brief the chief supplies follows the preamble. The preamble is not a fleet-wide brief for the rails. Text a lane reads after it starts does not settle which skill it follows: a model that rightly trusts the skill it was invoked with over a later redirect stops instead of switching. So the swap happens in the prompt itself. Copilot hands `userPromptSubmitted` an interactive skill invocation already expanded (`<skill-context name="issue-start">`, `Base directory for this skill: <dir>`, the body, `ARGUMENTS: <args>`), and the guard's `modifiedPrompt` replaces that block with the same shape built from the `SKILL.md` Lite uses before the first model turn: `<skills_dir>/<name>/SKILL.md` for the four issue skills when `skills_dir` is set, else this checkout's `skills/<name>/SKILL.md`. The session's `skill.invoked` event still names the folder the CLI resolved; the lane's first user message carries lite's base directory and body. This covers every session app-launcher-lite's session-host lists, a Board start included, because those sessions work on lite's GitLab repos. The `preToolUse` deny stays as the backstop for anything that reaches the full fleet's helpers anyway.

The chief is the launcher session whose working directory is the chief's folder and whose id `chief_ops.py chief-sid` names. The chief's folder is Lite's `fleet_config_dir` setting, read from `config/webapp_config.json`, or this `copilot/` folder when the setting is empty or the file is missing. Every session elsewhere is allowed before any subprocess runs. A fact the guard cannot read allows the action and is logged to stderr.

`chief_ops.py wake` prints `WAKE=doorbell ...` or `WAKE=waiter doorbell=off|unknown` from the launcher's `chief_doorbell` switch (`chief/mailbox.py`'s `resolve_wake_mode`, verbatim). The lite chief has no background waiter, because a background shell waking the agent is still an unknown probe item. Its backup is the launcher's fallback wake (Settings > Chief > Fallback check, `chief_fallback_minutes`, default 30 minutes, 0 = off): the launcher rings the idle chief once when an event has waited that long or worker slots sit free beside `queued` plan rows, whether the doorbell is on or off. `wake` prints it on a second line, `FALLBACK_WAKE=on minutes=<N>`, `FALLBACK_WAKE=off` or `FALLBACK_WAKE=unknown`. Otherwise only Roberto's own messages wake it, and `inbox` is read at the start of every turn it gets.

The doorbell can ring a Copilot chief, with the owner's Settings > Chief > Doorbell switch on. app-launcher-lite's session host tracks Copilot's composer from the keys probed on CLI 1.0.114 and reports `composer_dirty` as `True`/`False`, or `None` when it cannot tell; the bell rings only on `False`. Against the live chief, idle with pending mailbox events, a ring was seen 3 seconds after the debounce, and the chief started a turn and claimed the event. A chief started or restarted through the launcher had a composer left unknown by its own `/chief` until the first ordinary message; the launcher no longer does that, once its session host runs that build. A person's half-typed `/cmd` or `#` mention still reads unknown, and the bell holds off. The item `composer_keys_doorbell` stays `unknown` in this repo's probe results until the owner runs `copilot_probe.py record` for it.

A missed wake surfaces on its own. A ring counts only when the session host confirms its submit; a deferred, unconfirmed or untaken one is logged in `webapp/chief-doorbell.log` as not delivered, and the bell rings again after its back-off (one minute by default, `chief_rering_seconds`). Every ring and every skip reason is logged there. When the oldest pending event has waited 15 minutes (`chief_unread_alert_minutes`) with the doorbell on, the log gets one warning naming the current skip reason, and the chief's row appears in the Board's Your turn with a `mailbox unread` chip, counted in the Board tab's badge, until the mailbox is read.

`chief_ops.py slots-idle` prints `SLOTS_IDLE=<n> free=<f> queued=<q>`, or `unknown` with a reason, plus `SLOTS_COVERED=slots-idle` when that question is open.

## Compaction

`chief_ops.py context [<sid>]` reads a session's context-window use where Copilot records it: the newest `session.usage_record` in the session's `events.jsonl`, as `round(100 * inputTokens / maxPromptTokens)`. The launcher session id is joined to Copilot's session through the `sessions-state.json` row the hook writes (`launcher_session_id`, newest `updated_at`), and the log is that row's `transcript_path`, else `~/.copilot/session-state/<id>/events.jsonl`. app-launcher-lite's own `/context` endpoint is not used, because it reads a statusline Copilot does not print. If any step can't be read (no row, no log, no usage record, a missing field), the reading is `percent=unknown` with the reason, never 0.

`compact-due` compares the chief's reading with the Settings threshold (`/api/board/chief-settings`, `auto_compact_threshold`; 0 means off) and prints `COMPACT_DUE`, `COMPACT_NOT_DUE`, `COMPACT_OFF` or `COMPACT_DUE=unknown`. `inbox` prints the same line when the caller is the live chief and the context is due or unknown. `self-compact` (the chief) and `lane-compact` (a dispatched lane) post `/compact <focus>` to the caller's own session behind `chief/compact.py`'s refusals. `self-compact` refuses on an unknown percentage, below the threshold, or when the handover log (`chief-handover.md`) or the plan is older than 10 minutes. `lane-compact` refuses without a fresh `lane-handoffs/<sid>.md`, or while a gate runs in the lane's tree. That gate state is the in-flight marker `gate_evidence.py run` writes, which is why the lite issue skills now run their gate through it. Copilot queues a slash command typed mid-turn and runs it at turn end; that is the probe's manual item `compact_queued_midturn`, unknown until recorded.
